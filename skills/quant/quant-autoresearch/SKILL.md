# Quant AutoResearch

## What this is

A self-driving research loop for quantitative strategy and factor discovery, adapted from Karpathy's
autoresearch paradigm. The agent acts as an autonomous researcher: it proposes a hypothesis, edits
the single mutable strategy file, runs a fixed-budget backtest, evaluates the result against a
predefined decision rule, keeps or reverts the change via git, archives accepted versions, and
repeats until interrupted.

This is different from ordinary code generation or a one-off backtest: the loop itself is the
product. The human sets the objective and constraints up front (metric, budget, data, risk limits);
the agent then owns every research step.

## 双模式（Explorer / Refiner）

The loop runs in one of two modes, set in `research.toml -> [mode] name` (default `explorer`):

- **Explorer（发散创新）**: for cold starts, stale baselines and factor-library expansion. Structural
  changes are allowed (new factor operators, signal logic, nonlinear combinations); crashes and
  failures are research samples. Decision rule = primary metric + constraints.
- **Refiner（收敛优化）**: for live-ready baselines and walk-forward tuning. Only parameter, filter,
  risk and feature changes are allowed — `check_integrity.py` hard-fails structural changes; the
  decision rule is multi-objective Pareto screening (Sharpe / Calmar / MaxDD / train consistency)
  plus a complexity penalty (marginal gain with a sizable diff is rejected).

Switch modes by editing `research.toml -> [mode] name` and committing the change with a reason;
treat it as a milestone-level decision, not a per-experiment toggle. The report header shows the
active mode.

## Project layout

A project created by `init_research.py` is a self-driving research org:

```
my-quant-research/
├── AGENTS.md        # this project's research protocol (the "program")
├── research.toml    # metric, decision rule, budget, engine command (fixed after setup)
├── data/            # point-in-time data, version-pinned in data/VERSION (read-only)
├── strategy.py      # THE single mutable file: signal generation + position sizing
├── backtest.py      # evaluation harness: runs the strategy, writes metrics.json (read-only)
├── experiments/     # per-run logs + metrics (gitignored)
├── results.tsv      # experiment ledger (gitignored)
├── versions/        # archived accepted versions + baseline (git-tagged)
├── reports/         # draft leaderboard / ledger / report skeleton (gitignored)
└── docs/            # committed final report and milestone records
```

The template harness (`backtest.py`) is a reference implementation: the evaluation contract
(signal interface, artifacts, metric keys) is defined by the project's own harness and documented in
its docstring. `report.py` tolerates common variations (e.g. custom `full_*` / `bench_*` /
`yearly` fields) and notes what it could not fill.

## Setup (once per project)

1. Scaffold the project. For a runnable demo, add `--sample-data`:

   `python scripts/init_research.py /path/to/my-quant-research --name my-strategy --metric sharpe --sample-data`

   For real research, skip `--sample-data`, place point-in-time data under `data/`, then pin it:

   `python scripts/init_research.py /path/to/my-quant-research --pin-data`

2. Run scripts with the project's own Python environment (e.g. `uv run python ...` or
   `<project>/.venv/bin/python ...`), not a global interpreter.
3. Sanity-run the harness once manually to confirm the engine command in `research.toml` works.
4. Establish the baseline (no code changes yet):

   `python scripts/run_experiment.py /path/to/my-quant-research --baseline --message "baseline"`

5. Read `references/protocol.md`, confirm the metric and decision rule match the objective, then
   report setup complete and start the loop.

Do not modify `data/`, `backtest.py`, or `research.toml` during an autonomous run; they are the
evaluation contract. `strategy.py` is the only file you edit per experiment (see `allowed_files` in
`research.toml`).

## The experiment loop

For every iteration, in order:

1. **Hypothesize.** State one falsifiable hypothesis with economic rationale, the exact knob to
   change, and the expected effect. One idea per run — never bundle changes. If stuck for ideas,
   read `references/hypotheses.md`.

2. **Implement.** Make the smallest edit to `strategy.py` that tests the hypothesis. Keep diffs
   reviewable. Run `python scripts/check_integrity.py <project>` and fix hard failures (leakage,
   data version mismatch, out-of-scope files) before running.

3. **Run.** Execute the experiment:

   `python scripts/run_experiment.py <project> --message "H-<n>: <claim>（旋钮：<change>，预期：<effect>）"`

   The script commits your change, runs the backtest under the fixed time budget, applies the
   decision rule, and either keeps (archive + git tag) or reverts the change. It appends a row to
   `results.tsv`. If the run crashes, fix obvious bugs and re-run; if the idea is fundamentally
   broken, log it and move on.

4. **Diagnose.** After each run, read `experiments/<run_tag>/metrics.json` and `run.log`. Classify
   failures using `references/diagnostics.md` and feed the diagnosis into the next hypothesis. This
   is where the compounding value lives.

5. **Repeat. Never stop on your own.** Do not ask the human "should I continue?". Keep going until
   interrupted, `max_iterations` is reached, or a blocking condition occurs (missing data,
   permission, dependency install, disk full). If you run out of ideas, re-read the references,
   combine near-misses, revisit the literature, or re-derive hypotheses from past failures.

## Decision rule

`run_experiment.py` keeps a change only when, mechanically:

- the primary metric improves by at least `min_improvement` relative to the best accepted result;
- every configured constraint passes (e.g. max drawdown, turnover, exposure);
- the optional significance gate passes (`min_t_stat` when set);
- and the change is simpler-or-equal for comparable gains (your judgment, recorded in the run
  description).

In refiner mode the rule is stricter: constraints plus Pareto dominance over
Sharpe / Calmar / MaxDD / train consistency and a complexity penalty (`references/protocol.md`).

Full definitions, validation design (walk-forward, frozen OOS), and statistical caveats live in
`references/protocol.md`. Do not hand-edit the decision rule during a run.

## Integrity (non-negotiable)

- Signals may only use information available at bar `t`; positions execute at `t+1`.
- No survivorship bias: universe membership must be point-in-time.
- Costs (commission + slippage) must be included in the harness.
- The data version must stay pinned; changing data invalidates prior results.
- Never tune on the OOS test segment; it is frozen.

`check_integrity.py` enforces heuristics; the full checklist is in `references/integrity.md`. A
leakage bug turns the whole loop into noise — treat integrity violations as hard failures.

## Reporting and archive

- Every accepted version is snapshotted to `versions/v<N>/` and git-tagged `v<N>`; the baseline is
  `versions/v0/`. Provenance = code commit + data version + config hash + metrics.
- The experiment ledger lives in `results.tsv` (raw) and `reports/experiment_log.md`
  (human-readable). The ledger is never the research report.
- `python scripts/report.py <project>` writes the leaderboard and ledger; use `--report` to
  generate the human-readable research report skeleton at `reports/research_report.md`.
- `reports/` is draft working memory (gitignored). Publish the final report to `docs/` with
  `report.py --report --publish` (never overwrites an existing file), polish it, and commit it.
- On data re-scope or campaign restart, run `python scripts/milestone.py <project> --message ...`
  (archives the ledger, tags the state, records `docs/milestones.md`), then re-run the baseline.
- If the final recommendation differs from the last accepted version (e.g. a manually committed
  refinement), commit it with message prefix `recommend: ...` and designate it via `--final HEAD`;
  state why in the report.
- Choose the recommended final strategy explicitly with `--final` (default `HEAD`; also `v<N>`,
  `best`, or a git ref/commit). The report's final-parameters/rules section and charts follow this
  choice — use it when the recommendation differs from the last accepted version or the mechanical
  best (e.g. a simpler or more robust earlier version). If `HEAD` is not an accepted state, the
  script falls back to the last accepted version and says so.
- Before finishing a session, complete the report: fill every TODO section in the language set by
  `research.toml -> report.language` (default `zh`), reorganize sections to match the actual
  research, and include the summary, data background, design rationale, final parameters and rules,
  findings, comparisons, sensitivity analysis, risks/limitations, and reproduction steps.
- The report skeleton auto-fills a key-metrics quick-view table (baseline/final/best), charts
  (equity, drawdown, yearly returns, rolling Sharpe) and a yearly returns table from the final
  version's backtest artifacts; charts require matplotlib + pandas in the project environment.
- The skeleton also auto-fills a version-evolution table (v0..vN with OOS/train/full metrics), a
  train/OOS/full-sample summary, a configurable benchmark comparison, an offline cost-sensitivity
  grid (OOS and train), and an overfitting diagnostics block; research.toml and strategy.py are
  placed in appendices so the body stays readable. Missing artifacts are noted in the report.
- For factor-based projects, the harness can emit an optional `factor` block in metrics.json; the
  report then auto-renders a factor analysis section (IC/RankIC/ICIR, Rank IC decay, quantile
  performance) with charts. Schema: `references/protocol.md` section 9.
- The report closes the evidence chain with a gate check table (baseline improvement, constraints,
  OOS/IS ratio, train/OOS consistency, DSR) plus a TODO for the agent's continue / kill / promote
  recommendation.
- The report also auto-fills, when the harness provides the artifacts (reference harness does):
  a buy-and-hold benchmark comparison (alpha/beta/IR/excess return), an offline cost-sensitivity
  grid on the OOS segment (needs a `gross` returns column), and an overfitting diagnostics block
  (trials, acceptance rate, final t-stat, OOS/IS ratio, DSR heuristic). Missing artifacts degrade
  gracefully.

## Resuming a session

When the user reopens a project, read `AGENTS.md`, `research.toml`, and `results.tsv`, identify the
last accepted state, and continue the loop without re-doing setup.

## Resources

Read references only when needed:

- `references/protocol.md` — the full experiment protocol (metric, validation, decision rule,
  budget, crash policy, autonomy). Read at setup and whenever the decision rule is in doubt.
- `references/integrity.md` — backtest integrity checklist. Read before implementing signal code
  and when reviewing any diff.
- `references/hypotheses.md` — hypothesis playbook. Read when generating ideas or stuck.
- `references/diagnostics.md` — failure taxonomy and diagnosis workflow. Read after weak/failed runs.

Scripts (all take the project directory; run with `--help`):

- `scripts/init_research.py` — scaffold a project, generate sample data, pin the data version.
- `scripts/run_experiment.py` — run one experiment: commit, backtest, decide, keep/revert, archive.
- `scripts/check_integrity.py` — static integrity and scope checks before a run.
- `scripts/report.py` — leaderboard, human-readable experiment ledger, and research report skeleton
  (KPI/evolution/summary tables, benchmark, charts, yearly returns, cost grid, overfitting
  diagnostics, explicit final version via `--final`, publish via `--publish`).
- `scripts/milestone.py` — archive the ledger, tag the state and record `docs/milestones.md` when
  re-scoping data or restarting a campaign; then re-run the baseline.

## Example session

User: "Launch an autonomous research session on my ETF momentum strategy. Target: improve net Sharpe
over the current baseline. I will be back in the morning."

Agent: scaffold/verify the project, run the baseline, then drive the loop all night — momentum
windows, volatility scaling, cost-aware turnover reduction, regime filters — keeping only sound
improvements, archiving each accepted version, and leaving a leaderboard and report behind.
